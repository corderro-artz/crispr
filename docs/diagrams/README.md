# Diagrams

The `.mmd` files here are the source. The SVGs beside them are generated, and
the README embeds the SVGs through a `<picture>` so the reader gets the variant
that matches their colour scheme.

```bash
node docs/diagrams/build.mjs    # re-render every diagram (needs network: npx mermaid-cli)
node docs/diagrams/check.mjs    # verify without rendering (no dependencies)
```

**Edit the `.mmd`, never the SVG.** Before `build.mjs` existed the SVGs were
generated by nothing — the README called the `.mmd` the source with no script
behind it and no check, so the quick way to fix a wrong word in a picture was to
edit the picture, and the `.mmd` quietly stopped being the source of anything.

`check.mjs` is what keeps the caption honest. It fails when:

- a word the `.mmd` puts in a label is missing from either SVG, including a word
  split across two lines by wrapping;
- either SVG carries Mermaid's stock palette, or is missing this product's —
  i.e. it was rendered without `theme.json`;
- either SVG is not well-formed XML.

It imports nothing but Node builtins, so it needs no install and no browser.

## Theme

`theme.json` holds the colours. Every value is a stated mix of two core brand
tokens, recorded in its `derivation` field, so it can be re-derived rather than
remembered. The tokens themselves live at
[vaporsoft.dev/brand/palette.json](https://www.vaporsoft.dev/brand/palette.json).

Two settings in `build.mjs` are load-bearing and easy to undo by accident:

- `htmlLabels: false` emits `<text>` rather than `<foreignObject>`. A
  foreignObject is not rendered when an SVG is loaded through an `<img>`, which
  is how GitHub serves README images — HTML labels are a diagram that can come
  out silently empty.
- `wrappingWidth: 160` keeps the graph narrow enough to stay legible in an
  ~830px README column. Do not lower it: Mermaid escapes a second time when it
  wraps, and wraps by character, so a narrower setting splits `&lt;` across two
  tspans and the picture shows the raw entity instead of the `<`.
